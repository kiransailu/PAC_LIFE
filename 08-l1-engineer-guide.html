L1 Engineer's Guide — Pacific Life AppDynamics → OpenTelemetry/Grafana

Read this first if you are new to the project. It explains every tool, where it runs, who owns it, how the pieces connect, where we are today, and what "done" looks like. Diagrams are plain text so they survive DOCX/email.

1. The one-paragraph version

Pacific Life pays for AppDynamics (AppD) to monitor 10 applications. The contract ends 31 Dec 2026 and they do not want to renew. Our job (Trace3) is to replace the AppD agent inside each app with an OpenTelemetry (OTel) agent, send that data through Grafana Alloy (a collector Pacific Life already runs) into Grafana Cloud (which Pacific Life already owns), rebuild the same alerts/dashboards there as code, prove the app teams can see the same things they saw before ("functional parity"), make sure alerts still create ServiceNow tickets in the right team's queue, and hand Pacific Life an evidence pack so they can safely let AppD expire.

2. Glossary — every tool and term, in plain words

Monitoring concepts

Term Plain meaning
APM (Application Performance Monitoring) Watching what happens inside an application: which requests came in, how long they took, which failed, which database/API calls they made.
Trace The full story of one request as it travels through the app (and other services). Made of spans.
Span One step inside a trace, e.g. "HTTP GET /api/quote took 120 ms" or "SQL SELECT took 15 ms". Has a name, start/end time, status (OK/ERROR), and attributes (key=value, like http.route=/api/quote).
Metrics Numbers over time: requests per second, error %, CPU. Cheap to store, good for alerting.
Logs Text lines the app writes. Useful when correlated to a trace via trace_id.
RED Rate (calls/min), Errors (%), Duration (latency, e.g. p95). The three golden numbers per service/endpoint.
p95 95% of requests were faster than this value. Better than "average" because it shows the slow tail.
Instrumentation The code that produces traces/metrics/logs. Zero-code / auto-instrumentation = an agent injected at startup does it for you; no app code changes.
Dual-run Two monitoring agents in the same process at the same time (old + new) so you can compare. Possible for Java and Python; impossible for .NET.
Cardinality Number of unique label combinations in a metric. Too many (e.g. a user ID in a span name) = huge cost. We guard against it.
Tail sampling Deciding after a trace completes whether to keep it (keep all errors, all slow ones, 10% of normal). Saves cost.
PII Personal data (SSN, card numbers, emails). Must be scrubbed before it leaves Pacific Life's network.

AppDynamics terms (the thing we are replacing)

AppD term Meaning OTel/Grafana equivalent
Controller The AppD server/UI where everything is stored and viewed. Stays up until Dec 31 as fallback. Grafana Cloud
Agent Library attached to the app (Java -javaagent, .NET CLR profiler, Python pyagent) that sends data to the Controller. This is what we remove. OTel zero-code agent
Business Transaction (BT) A named entry point into the app, e.g. "Get Quote", "Bind Policy". AppD auto-detects them and lets you add custom split rules (by URL segment, HTTP header, or Java class/method = "POJO"). A span-metrics series keyed on service.name + span_name (http.route). Custom split rules are rewritten as OTTL rules in the pipeline.
Health Rule A condition on a BT or tier: "error rate > 2% for 5 min". Can be static (fixed number) or dynamic baseline (AppD learns "normal"). Grafana alert rule on span-metrics. Baseline rules need a decision: static threshold or Grafana ML.
Policy / Action "When health rule X fires → create ServiceNow incident in group Y". Grafana notification policy + contact point (webhook to ServiceNow).
Snapshot A captured slow/error request with full detail. A trace in Tempo, kept by tail sampling.
Dashboard Visual panels. Grafana dashboard (built from a Terraform template).
Information Point / Data Collector Custom business values captured from code (e.g. "policy amount"). Span attribute → may need app code change (Pacific Life owns) or becomes an exception.
EUM / DB Visibility / Analytics / Synthetics Browser monitoring, DB-server monitoring, business analytics, synthetic checks. No zero-code equivalent — Pacific Life must decide in-scope or exception (Discovery Q2).

OpenTelemetry (OTel) terms (the new standard)

Term Meaning
OpenTelemetry Open-source, vendor-neutral standard for producing telemetry. Owned by CNCF, not a vendor. Every APM vendor now accepts it.
OTLP OpenTelemetry Protocol — the wire format. gRPC on port 4317, HTTP on port 4318.
OTel Java agent A .jar added with -javaagent: at JVM start. Auto-instruments Spring, Tomcat, JDBC, JMS, etc.
OTel .NET auto-instrumentation A CLR profiler registered via COR_PROFILER env vars. Auto-instruments ASP.NET, HttpClient, SQL. Only one profiler per process — this is why AppD and OTel cannot coexist on .NET.
OTel Python distro opentelemetry-instrument your_app wrapper that monkey-patches Django/Flask/FastAPI, requests, DB drivers. Weakest coverage of the three.
Resource attributes Metadata about who is sending: service.name, app.id, deployment.environment. Set via OTEL_RESOURCE_ATTRIBUTES.
OTel Collector A standalone process that receives, processes, and exports telemetry. Grafana Alloy is an OTel Collector distribution (plus more).
OTTL OpenTelemetry Transformation Language — small statements run inside the collector to rename spans, set/delete attributes, redact. We use it to reproduce AppD BT rules and PII redaction. Example: set(name, "BT:quote") where IsMatch(attributes["url.path"], "^/api/quote").

Grafana stack terms

Term Meaning Where it runs
Grafana Alloy Grafana's collector. Reads OTLP, Prometheus, logs; processes; forwards. Config files end in .alloy. Two places: on every app host (already deployed by Pacific Life) and as a regional pipeline on EKS.
Amazon EKS AWS-managed Kubernetes. Hosts the regional Alloy pipeline (3 replicas, behind an internal NLB). AWS, Pacific Life account
Grafana Cloud Grafana's SaaS. Pacific Life owns the account and pays for ingest. Contains the four services below. SaaS (Grafana-hosted)
Tempo Trace storage/query. Has a metrics-generator that turns spans into RED metrics automatically. Inside Grafana Cloud
Mimir Prometheus-compatible metrics storage. Receives host metrics and the span-metrics Tempo generates. Alert rules query Mimir. Inside Grafana Cloud
Loki Log storage/query. Inside Grafana Cloud
Span-metrics Metrics Tempo generates from traces: traces_spanmetrics_calls_total (rate+errors) and traces_spanmetrics_latency_bucket (duration), labelled by service, span_name, status_code. These are our BT equivalents. Mimir
Application Observability Grafana Cloud UI that shows a service map and RED per service/operation from span-metrics. Nice-to-have; Q9 confirms it's on. Grafana Cloud
Grafana Alerting Alert rules (query + threshold), contact points (where to send), notification policies (routing by labels). Grafana Cloud
TraceQL / PromQL / LogQL Query languages for Tempo / Mimir / Loki.

Delivery tooling

Term Meaning
Terraform Infrastructure-as-code. We describe dashboards, alert rules, contact points in .tf files; Terraform creates them in Grafana via the Grafana provider. Repeatable for all 10 apps and the 343 after.
Azure DevOps (ADO) Pacific Life's Git + CI/CD. Our Terraform and Alloy configs live here; pipelines run plan/apply. State in Azure Storage.
Helm Kubernetes package manager. Deploys the Alloy pipeline to EKS with values.yaml.
ServiceNow (SNOW) Pacific Life's ITSM. Alerts become incidents assigned to an assignment group (a team queue). Also holds the CMDB.
CMDB Configuration Management Database. Source of truth for APP_ID and environment per host/app.
CAB Change Advisory Board. Approves production changes. Has a lead time we must plan around.
Hypercare Fixed window (10 business days) after prod cutover when we watch closely and can roll back fast.
Change freeze Dec 21 – Jan 3: no production changes. So Dec 18 is our real last change date.
FPC Functional Parity Checklist — our per-app acceptance document. If it isn't ticked and signed, the app isn't done.

5. Follow one request end-to-end

Take GET /api/quote/123 on APP-01 (Java) in prod after cutover.

 1. Tomcat receives the request.
    OTel Java agent (loaded via -javaagent) creates a SERVER span:
      name = "GET /api/quote/{id}"   http.route="/api/quote/{id}"   url.path="/api/quote/123"
      resource: service.name="app01-quote-api"  app.id="APP-01"  deployment.environment="prod"
    Child spans: JDBC SELECT (CLIENT span), outbound HTTP to rating service (CLIENT span).
    Logback appender sends log lines with trace_id as OTLP logs.

 2. Agent exports the finished trace over OTLP gRPC to 127.0.0.1:4317  → HOST ALLOY.

 3. HOST ALLOY: adds host.name; inserts app.id/deployment.environment if agent didn't; batches;
    sends to the regional pipeline NLB (TLS).

 4. EKS PIPELINE:
    enrich  → service.namespace="APP-01" (so Grafana groups services per app)
    bt_rules→ APP-01 rule: url.path matches ^/api/(?P<bt>[^/]+) → bt.name="quote"
              → span name becomes "BT:quote"; if header x-channel=mobile → "BT:quote@mobile"
              (this is exactly the AppD BT "Quote (mobile)")
    redact  → url.full loses "?..." ; any SSN-looking string → "[SSN]" ; SQL literals → "?"
    sampling→ waits 15s for the whole trace; keeps it if ERROR / >2s / 5xx / lucky 10%
    batch   → otlphttp → https://otlp-gateway-...grafana.net/otlp  (basic auth: instance id + token)

 5. GRAFANA CLOUD:
    Tempo stores the trace (if sampled).
    Tempo metrics-generator increments:
      traces_spanmetrics_calls_total{service="app01-quote-api", span_name="BT:quote", status_code="STATUS_CODE_OK"}
      traces_spanmetrics_latency_bucket{... le="0.25"}
    → written into Mimir. Loki stores the log lines with trace_id.

 6. ALERTING (every 60s):
    rule "APP-01 | BT:quote | error rate > 2%" runs PromQL against Mimir.
    If true for 5 min → alert fires with labels app_id=APP-01, severity=critical.
    Notification policy matches app_id=APP-01 → contact point "snow-app-01-prod" (webhook)
    → ServiceNow creates incident, assignment_group="PL-Quote-Platform-L2".

 7. HUMAN: opens the APP-01 Golden Signals dashboard → sees BT:quote error % spike →
    clicks into Tempo "recent error traces" → opens the trace → sees the JDBC span failing →
    clicks the trace_id → Loki shows the stack trace log line.

That chain — agent → host Alloy → EKS pipeline → Tempo/Mimir/Loki → alert → ServiceNow — is the whole project. Every deliverable configures one link of it.

        ▼                                                          APP-02: POJO method, JMS queue

        ▼

        ▼

Why BT rules live here and not in app code: 10 apps × many BT rules = one place to maintain, no app redeploys, and the same pattern scales to 343 apps. Why redaction is here: it's the last Pacific Life-controlled hop before data leaves for SaaS.

Trade-off to know: tail sampling drops traces, and Tempo's metrics-generator only counts what arrives. So span-metrics reflect the sampled set unless we generate span-metrics inside the pipeline before sampling (a connector we can enable — Pacific Life decides, Q11).

11. Alert → ServiceNow path (the parity test that matters most)

 Mimir metric crosses threshold for 5m
   → Grafana alert rule fires   labels: app_id=APP-01 severity=critical bt=BT:quote environment=prod
   → Notification policy tree:  root (platform team) ──child: app_id=APP-01 & environment=prod──▶
   → Contact point "snow-app-01-prod" (webhook, basic auth)
   → ServiceNow inbound API creates Incident
        short_description = "[FIRING] APP-01 error rate > 2%"
        assignment_group  = "PL-Quote-Platform-L2"     ◀── must equal what the AppD policy used
   → App team sees it in the same queue as before.  ✔ parity

We test this per app with the routing-test rule, record the incident number and group in FPC §4, then disable the test rule.

16. Ten things to remember

  1. We are replacing the agent inside the app, not the apps and not Grafana — Grafana Cloud already exists.
  2. BT = span-metrics series (service + span_name). If traces_spanmetrics_* isn't in Mimir, nothing else works.
  3. .NET can't dual-run. Validate side-by-side or canary; rollback is a redeploy.
  4. Parity is defined by the FPC, not by feelings. Get it approved before touching Tranche 1.
  5. An alert is parity only if it lands in the same ServiceNow group. Test per app.
  6. Everything is code in Azure DevOps — no clicking in Grafana UI for anything that must survive.
  7. PII is scrubbed in the EKS pipeline, the last Pacific Life-controlled hop.
  8. Tail sampling saves money but changes what metrics count — decision for Pacific Life.
  9. AppD Controller stays as fallback until Dec 31 — keep access, use it for the baseline and the agent-removal proof.
  10. Dec 18 is the last change date (freeze Dec 21 – Jan 3); draft evidence pack by Nov 27 so the non-renewal decision is informed.
